## 1. Что это

**ESP8266-Autowatering2** — прошивка контроллера автополива растений на ESP8266
(NodeMCU / Wemos D1 mini, flash 4 МБ).

Железо:

* 4 канала помп (4 реле) — GPIO задаются в настройках;
* 1 дискретный датчик **низкого** уровня воды (поплавок/геркон, замыкание на GND);
* Wi-Fi 2.4 ГГц, веб-интерфейс на самом устройстве (без облака и приложений).

Пользовательские требования (реализованы, менять без явного запроса нельзя):

1. Подключение к Wi-Fi; если Wi-Fi не настроен — поднимается **открытая** точка
   доступа `AutoWater-XXXXXX` с captive-порталом, требующим настроить Wi-Fi
   (никакой авторизации).
2. В шапке интерфейса — текущее время (NTP) и состояние датчика уровня.
3. Задачи полива: время старта, длительность (сек), период повторения (дни),
   активность, статус, кнопка ручного пуска (пуск = включить поток на
   настроенную длительность, **не меняя** статус/расписание задачи).
4. Задачи и их статусы (время последнего полива) сохраняются при отключении
   питания.
5. Вкладка ручного управления: для каждого канала пуск на N секунд и остановка.
6. Вкладка настроек: Wi-Fi, пины помп (по умолчанию — те, что при старте в
   низком уровне), пин датчика уровня и полярность сигнала.

Текущий статус: **прошивка собрана**, бинарник лежит в
`firmware/autowatering-esp8266.bin` (см. `firmware/build-info.txt`).
Прошить в чужой COM-порт из песочницы нельзя — прошивка выполняется у
пользователя командой `tools/flash.sh` (по умолчанию `COM7`, 921600).

## 2. Стек и версии

* Язык: C++11 (Arduino-стиль, без исключений/RTTI), без динамического JSON.
* Фреймворк: Arduino core for ESP8266. Проект совместим с **2.4.2** (используется
  офлайн-сборщиком) и **3.1.x** (PlatformIO по умолчанию).
* Библиотеки: только встроенные — `ESP8266WiFi`, `ESP8266WebServer`, `DNSServer`,
  `EEPROM`. Внешних зависимостей нет (осознанно: сборка без интернета).
* Фронтенд: `web/index.html` — один файл, чистый HTML/CSS/JS (fetch + form-urlencoded),
  сжимается gzip в `src/page_html.h` (экономия flash/RAM при отдаче по HTTP).

## 4. Модель данных (EEPROM)

Одна структура `Store` (`src/app_config.h`) в секторе эмуляции EEPROM
(`EEPROM.begin(1024)`), защищена `magic`/`version`/`crc32`.
Раскладка: `magic`, `version`, `Settings cfg`, `TaskCfg tasks[8]`, `crc`.

* `Settings`: `ssid`, `pass`, `ntpServer`, `tzOffsetMin` (минуты, 180 = МСК), `sensorPin`,
  `sensorActiveLow`, `sensorPullup`, `blockWhenLow`, `catchupHours`, `maxRunSec`,
  `ch[4]` (`pin`, `activeLow`).
* `TaskCfg`: `used`, `enabled`, `channel`, `hour`, `minute`, `periodDays`,
  `durationSec`, `lastRun`, `nextDue` (оба — **локальное** unix-время).

Инварианты:

* Любое изменение `g_store` в API-обработчике должно сопровождаться
  `storage_save()`.
* После правки параметров задачи — `sched_task_changed(idx)` (сбрасывает
  `nextDue`, чтобы расписание пересчиталось от «сейчас»).
* Ручной пуск задачи (`/api/task/run`) **не трогает** `lastRun`/`nextDue`.
* Пины: 0…16, запрещены 6…11 (flash). Дубликаты между помпами и датчиком
  запрещены (`handle_config_save`).
* По умолчанию пины помп = 4, 5, 12, 14 (при старте ESP8266 — низкий уровень),
  датчик = 13. `activeLow = 0`: помпа включается **высоким** уровнем, поэтому в
  момент старта (0 В) все реле выключены. Инверсия включается в настройках для
  модулей реле с активным низким уровнем.

## 5. Логика времени (важно!)

* Внутри прошивки время всегда считается через `src/clock.*`:
  * `clock_utc()` — UTC-секунды. Источник №1 — NTP (`configTime(0, 0, server)`,
    ядро отдаёт UTC), источник №2 — время с телефона (`clock_set_from_phone()`),
    которое «идёт» от `millis()` и живёт до перезагрузки; иначе время неизвестно.
  * `clock_local()` = UTC + `tzOffsetMin*60`. Это «локальные секунды эпохи»
    (wall clock). Пояс **не передаётся ядру** — иначе в 2.4.2 и 3.x получается
    разное поведение `time()`/`localtime()`.
* Всё расписание и хранение (`lastRun`, `nextDue`) — в локальной шкале.
  Арифметика суток — целочисленная: `day = local/86400`,
  `clock_at_time(local, days, h, m) = (day+days)*86400 + h*3600 + m*60`.
  Никаких `mktime`/`localtime` (нет DST-сюрпризов, работает одинаково на всех ядрах).
* Смена пояса не сдвигает расписание: задача «08:00» остаётся на 08:00 местного.
* UI **не должен** форматировать время сам: сервер отдаёт готовые строки
  (`time`, `date`, `lastStr`, `nextStr`) и `timeSrc` (`ntp`/`manual`/`none`).
  Именно из-за форматирования `new Date(epoch)` в браузере раньше появлялся
  сдвиг «08:00 → 11:00».
* `DEFAULT_TZ_OFFSET_MIN = 180` (UTC+3, МСК), `STORE_VERSION = 3`
  (версия 3 добавила `Settings.name` и `ChannelCfg.name` — имена модуля и каналов);
  при смене версии формата EEPROM сбрасывается к умолчаниям.
* `POST /api/time` (`now` = `Math.floor(Date.now()/1000)`, опционально `tz` в
  минутах = `-getTimezoneOffset()`) — кнопки «Время с телефона» в настройках и в
  баннере (режим настройки/нет времени). Если NTP уже синхронизирован, ручное
  время игнорируется (NTP приоритетнее).

## 6. REST API (кратко)

`GET /api/state`, `GET /api/config`,
`POST /api/task` (`id=-1` для новой), `POST /api/task/del`, `POST /api/task/run`,
`POST /api/ch` (`ch`, `sec`; `sec=0` — стоп),
`GET /api/export` — настройки, имена каналов и задачи одним JSON (без Wi-Fi),
`POST /api/import` — импорт: те же поля, что у `POST /api/config`, плюс
`t0…t7` (задача строкой `ch,h,m,dur,pd,en,last,next`) и `status=1` (переносить
`lastRun`/`nextDue`). **JSON разбирает браузер**, устройство принимает уже
плоскую форму — не добавляйте JSON-парсер на ESP8266, `transfer_task_decode()`
специально сделан без выделения памяти. Импорт проверяет всё до применения:
при ошибке конфигурация остаётся прежней (не повторяйте `POST /api/config` +
`POST /api/task` по одному — это даёт полуимпортированное состояние).

`GET /api/scan` (`start=1` — начать поиск; ответ `running` / `done` / `idle`,
`nets[] = {ssid, rssi, enc}`; сканирование **асинхронное** — `WiFi.scanNetworks(true, true)`
и опрос `WiFi.scanComplete()`, иначе блокирующий скан рвёт страницу в режиме точки доступа),
`POST /api/time` (`now`, `tz`), `POST /api/config`, `POST /api/wifi`,
`POST /api/factory`, `POST /api/reboot`.

Имена: в `/api/state` — `name` (имя модуля, `""` = не задано) и `appName` (название
прошивки `FW_NAME`), у канала `nm` (имя канала, `""` = «Канал N»); в `/api/config` —
`name` и `ch[].name`; в `POST /api/config` — `name` и `chN_name`. Имя канала
выводится рядом с номером («Канал 1 · Орхидеи»), у канала без имени остаётся «Канал N», пустое имя модуля — на «Автополив». Имя модуля
используется и как префикс точки доступа (`<имя>-XXXXXX`, до 24 байт имени).
Имена хранятся как есть (UTF-8) и **обрезаются по границе символа** функцией
`text_set` — не заменяйте её на `strncpy`, иначе получите битую кириллицу.

Элемент `ch[]` в `/api/state`: `i`, `pin`, `inv`, `on`, `rem` (осталось сек),
`task` (id задачи или -1), `seq` (счётчик выключений канала), `rsn`
(`timer` | `manual` | `low` | ""), `run` (сколько секунд реально работал).
UI сравнивает `seq`: новое значение = показать уведомление о выключении
(«полив завершён», «низкий уровень воды», «остановлен»). Ручная остановка из UI
показывает тост сразу и подавляет событие канала на 5 секунд, чтобы не было
дубля. Не убирайте `seq/rsn/run` — на них держатся уведомления.
Формат — `application/x-www-form-urlencoded` (на ESP разбирается `server.arg()`,
JSON-парсера нет намеренно). Ответы — JSON, ошибки `{"ok":false,"error":"..."}`.

Полная таблица — в `README.md`.

## 7. Сборка

### 7.1 PlatformIO (для пользователя)

```bash
pio run
pio run -t upload   # порт/скорость в platformio.ini: COM7 / 921600
```

### 7.2 Офлайн-сборка (как собран бинарник в репозитории)

```bash
TOOLCHAIN_DIR=<каталог с bin/xtensa-lx106-elf-g++> \
CORE_DIR=<каталог Arduino-2.4.2> \
./tools/build_firmware.sh
```

Подводные камни (уже учтены в скрипте, не откатывайте):

* **Имена объектных файлов обязаны сохранять расширение** (`Foo.cpp.o`,
  `bar.c.o`): linker script ядра раскладывает код во flash по маске
  `*.cpp.o(.text*)`. Если назвать `Foo.o`, всё уедет в IRAM и линковка упадёт с
  `section .text will not fit in region iram1_0_seg`.
* `tools/sdk/ld/eagle.app.v6.common.ld` генерируется из `.h` перед линковкой
  (`gcc -CC -E -P -DVTABLES_IN_FLASH`).
* В начало `.irom0.text` скрипт **добавляет 8 зарезервированных байт**
  (`__crc_len`/`__crc_val`): ядро 3.x делает это штатно, в 2.4.2 их нет, а
  `tools/elf2bin.py` пишет туда контрольную сумму образа. Без резерва
  затираются первые 8 байт кода, и прошивка падает. Проверка:
  `__crc_len` = полный размер `.bin`, `__crc_val` совпадает с пересчётом CRC32
  (алгоритм `crc8266` из `elf2bin.py`).
* Приложение линкуется с `eagle.flash.4m.ld` → код по адресу 0x40201010, образ
  содержит `eboot` (0x0) + приложение (0x1000). Именно это делает
  `tools/elf2bin.py`.
* `tools/elf2bin.py` — вендорная копия из ядра 3.1.2 с двумя правками: список
  секций приложения без `.text1` и пропуск отсутствующих секций (ядро 2.4.2 не
  имеет `.text1`/`.rodata` в `eboot.elf`).
* Использованный кросс-компилятор: GCC 4.8.2 с C++ (`cc1plus`), т.е. сборка под
  ядро 2.4.2. Ядро 3.x с GCC 4.8.2 не собирается — для него только PlatformIO.

### 7.3 Интерфейс

```bash
python3 tools/embed_web.py     # после любой правки web/index.html
```

## 8. Прошивка

```bash
pip install esptool
./tools/flash.sh               # COM7, 921600, образ 0x00000
```

Эквивалент:

```bash
esptool.py --chip esp8266 --port COM7 --baud 921600 write_flash \
  --flash_mode dout --flash_freq 40m --flash_size 4MB \
  0x00000 firmware/autowatering-esp8266.bin
```

## 9. Проверки, которые стоит прогонять после правок

1. Сборка (`tools/build_firmware.sh` или `pio run`) без ошибок; размер
   `.irom0.text` < ~1 МБ, `.text` < 32 КБ, `.data + .bss` < 80 КБ.
2. `python3 tools/embed_web.py` — интерфейс упаковался.
3. Синтаксис JS: извлечь `<script>` из `web/index.html` и прогнать
   `node --check`.
4. UI в jsdom с фейковым API: шапка (время/датчик), список задач, каналы,
   заполнение настроек, POST-запросы по кнопкам, отсутствие ошибок JS.
5. Хост-тесты логики (без железа):
   ```bash
   make -C tests/host run
   ```
   Покрывают: дефолты и CRC хранилища, уровни/инверсию/лимиты помп, реакцию на
   датчик, расписание (первый запуск, период, догоняющий полив, пропуски,
   ручной пуск без изменения статуса, отсутствие времени).

## 10. Стиль и правила изменений

* C++11 без исключений/RTTI; никаких `new`/`delete` в рантайме, `String` — только
  для коротких JSON-ответов.
* Не блокировать `loop()` (`delay()` — только при перезагрузке).
* Все пользовательские строки интерфейса — на русском.
* Безопасность важнее удобства: при низком уровне воды полив запрещён, любое
  включение ограничено `maxRunSec`, после рестарта всё выключено.
* Не удаляйте `ReadAI.md`, `tools/elf2bin.py` и `firmware/build-info.txt` — это
  часть воспроизводимой сборки.
* Секретов в репозитории нет: Wi-Fi-креды хранятся только в EEPROM устройства.
